# Таймаути та відновлення зв’язку

У попередній версії клієнт обривав запит через 12 секунд і радив повторно натиснути ОК. При цьому сервер міг уже виконати дію. Відправлення нагадування чекало на зовнішній Telegram API до 10 секунд усередині `blockConcurrencyWhile`, затримуючи запити до того самого пета.

## Зміни

- Надсилання Telegram-повідомлення винесено з блокування; резервування й планування залишаються в захищеній частині.
- Перша спроба запиту має 15 секунд, повторна — 20; між ними коротка пауза. Бізнес-помилки й неправильна авторизація не повторюються.
- Нормальні зміни пета мають атомарне підтвердження запиту разом із записом стану. При повторі повертається поточний стан і попередній результат без повторного застосування.
- Підтвердження зберігаються окремими невеликими записами; прибирання прострочених записів проходить обмеженими порціями. Протягом доби підтвердження не витісняється новими діями. Клієнт зберігає нез’ясовані ID до 15 хвилин; у sessionStorage є лише хеш запиту, ID і час, без Telegram-сесії чи подарункового коду.
- Поповнення, переказ і зарахування подарунка мають власні атомарні підтвердження. Створення подарунка повторюється з тим самим `op` у наявному протоколі резервування.
- Команди пісочниці та швидкі рухи іграшки не повторюються автоматично, щоб не відтворювати застарілі жести.
- До трьох спроб відновлення стану після втрати мережі; повторна перевірка при події `online` і поверненні у вкладку.
- Фонове читання раз на 30 секунд, без накладання на активні запити. Службовий статус не озвучує пет.

Це виправляє виявлені місця затримки та небезпечний повтор. Точну причину конкретного скриншота без журналів живого запиту встановити неможливо.

## Перевірки

`npm test` і `npm run build`.

У Miniflare з реальним SQLite перевіряються повтори покупки, конкурентні однакові запити, сон без подвійного перемикання, переказ, поповнення та rollback при винятку після запису пета. В окремому тесті повільний Telegram API не утримує блокування.

`docs/detailed-preview/network-check.mjs` запускає справжній клієнт: відповідь на вже виконану покупку губиться, повтор використовує той самий ID, монети списуються один раз. Окремо перевіряється відновлення першого завантаження після двох збоїв мережі.
